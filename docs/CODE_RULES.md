# 项目代码规则

## 目标

本项目优先保证行为正确、可读、可维护，以及玩法参数来源一致。测试用于证明实现满足需求，不能替代对真实输入、状态流和模块边界的理解。

## 正确性与范围

- 实现应覆盖需求允许的所有输入和状态，不为某个测试样例硬编码，也不通过削弱断言掩盖缺陷。
- 如果需求、测试和现有实现互相冲突，先定位冲突并说明；不要用兼容分支同时保留两个相反行为。
- 优先复用现有实现、常量和稳定测试入口。一个值只保留一个可信来源，不为展示或临时修复复制状态。
- 先把逻辑写清楚，再提取确有复用价值的抽象。一次性操作留在调用处，不为假设中的未来场景增加配置或防御分支。

## 模块归属

- 公共逻辑拆到合适模块：
  - 游戏参数放 `src/constants/*`
  - 实体行为放 `src/entities/*`
  - 游戏运行时通用函数放 `src/game/utils.ts`
  - 通用展示格式化函数放 `src/utils.ts`
  - 运行时编排放 `src/game/runtime.ts`
  - React 外壳与展示放 `src/app/*`、`src/ui/*`，避免承载复杂玩法计算
  - 资源加载清单放 `src/assets/manifest.ts`，加载编排放 `src/assets/index.ts`

## 注释规范

- 注释只解释“为什么这样做”，不要复述代码本身。
- 以下场景必须补充注释：
  - 复杂判定或边界条件
  - 不直观的运行时约束
  - 临时兼容逻辑或有明确背景的实现
- 禁止无信息注释，例如“设置 x”“更新数据”这类直接复述代码的内容。

## 命名规范

- 变量、函数使用 `camelCase`。
- 类型、接口、组件使用 `PascalCase`。
- 共享常量、配置对象使用 `UPPER_SNAKE_CASE`。
- 布尔值优先使用 `is`、`has`、`can`、`should` 前缀。
- 事件处理函数优先使用 `handleXxx`。
- 工厂函数优先使用 `createXxx`。
- Jotai atom 统一使用 `xxxAtom`。

## TypeScript 规范

- 禁止显式使用 `any`。
- 优先使用精确类型；无法直接确定时，使用 `unknown` 后再做收窄。
- 公共导出函数的参数与返回值应保持清晰，避免“神秘对象”参数。
- 需要表达结构时，优先定义明确的 `type` 或 `interface`。

## Magic Number 规范

- 禁止在玩法逻辑、判定逻辑、运行时阈值中直接写含义不明的数字。
- 游戏数值优先抽到 `src/constants/*`，并沿用现有 `src/constants/combat.ts` 的组织方式。
- 模块内部只使用一次、但有明确语义的数字，也应提取为模块顶部具名常量。
- 允许直接保留少量基础数字：`0`、`1`、`-1`、`2`，以及明显的数组索引/循环步进值。
- Tailwind 或 JSX 中的尺寸值不做机械式全部抽离；只有在“重复出现”或“具备明确语义”时才提取为 UI 常量。

## 分级验证

选择能证明当前改动正确的最小检查集，并在影响范围扩大时升级：

- 所有改动：运行 `git diff HEAD --check`，并检查最终 diff 只包含任务范围。
- 纯文档：核对引用路径和命令真实存在，运行 `npm run lint:lines`。
- TypeScript / React：运行相关单测、`npm run typecheck` 和 `npm run lint`。
- 玩法、运行时或跨模块行为：完成相关单测后，最终运行 `npm test` 和 `npm run build`。
- 位图或 sprite：执行 `workflows/imagegen-project-asset.md` 的素材契约检查；只有代码或常量同时变化时才追加对应代码检查。

如果检查失败，继续修复当前改动导致的问题；对无关的既有失败，保留证据并明确报告。

## 素材与文档同步

- 新增或替换运行时素材时，同时检查 `src/constants/assets.ts`、`src/assets/manifest.ts`、`src/assets/index.ts` 和 `docs/SPRITES.md`。
- 修改地图片段、平台层级、奖励或可达性参数时，同时更新 `docs/map-generation.md`。
- 修改输入键位、HUD 快照字段、渲染顺序或运行时模块边界时，同时更新 `docs/ARCHITECTURE.md`。
